# ADR-001: Механізм контролю конкурентного бронювання лотів

- **Статус:** Approved
- **Дата:** 18.10.2026
- **Автор:** Островська К. П.
- **Пов'язані вимоги:** [SRS-FUN-09](../srs.md#srs-fun-09),
  [SRS-FUN-10](../srs.md#srs-fun-10),
  [SRS-NFR-CONS-01](../srs.md#srs-nfr-cons-01),
  [SRS-NFR-PERF-02](../srs.md#srs-nfr-perf-02)

## Context

Лот містить від 1 до 50 однакових одиниць товару, а ціна лота
знижується щохвилини. Під час досягнення привабливої ціни на один лот
одночасно надходять запити від користувачів і від лімітних ордерів.
SRS вимагає нуль подвійних продажів на 1 000 запитів до лота з 10
одиницями (SRS-NFR-CONS-01) та p95 ≤ 250 мс для резервування при 200
одночасних запитах (SRS-NFR-PERF-02). Кожна продана одиниця повинна
мати власний ідентифікатор для TTL резерву, QR-коду видачі та
підтвердження в B2B-системі (SRS-FUN-10, SRS-FUN-12).

Обмеження проєкту: один вузол PostgreSQL 16 (без кластера), розгортання
через Docker Compose на одному VPS, один розробник, Redis уже
присутній у стеку як кеш, pub/sub і сховище черг BullMQ.

## Alternatives

1. **Умовний атомарний `UPDATE` лічильника.**
   `UPDATE lots SET available = available - 1 WHERE id = $1 AND available > 0`.
   Атомарний і найпростіший у реалізації. Усі конкурентні транзакції
   очікують блокування одного рядка, тому затримка зростає лінійно з
   кількістю запитів; одиниця не має власного ідентифікатора, тож TTL
   резерву та QR-код потребують окремої таблиці й другого запиту.
2. **Оптимістичне блокування (стовпець `version`).**
   Не тримає блокувань, однак при 200 одночасних запитах успішним є
   один запит на кожну версію; решта отримує конфлікт і повторює
   спробу. Кількість повторів зростає квадратично, p95 перевищує ліміт.
3. **Розподілене блокування в Redis (`SET NX PX`, Redlock).**
   Знімає навантаження з СУБД, але створює два джерела істини: після
   спливу TTL блокування транзакція СУБД ще може тривати (GC-пауза, мережева
   затримка), що порушує взаємне виключення без fencing-токенів.
   Redis без AOF `appendfsync always` може втратити блокування під час
   рестарту.
4. **Серіалізація через чергу (одна черга BullMQ на лот).**
   Гарантує порядок FIFO, однак перетворює синхронний запит на
   асинхронний: клієнт очікує результат через WebSocket або polling,
   затримка дорівнює довжині черги, а динамічне створення черг на
   кожен лот ускладнює експлуатацію.
5. **`SELECT … FOR UPDATE SKIP LOCKED` над таблицею `lot_units`.**
   Кожна одиниця лота — окремий рядок. Транзакція блокує першу вільну
   одиницю, пропускаючи заблоковані іншими транзакціями, тому запити
   не очікують один одного.

## Decision

Обрано альтернативу 5. Резервування виконується однією короткою
транзакцією в Trading Service:

```sql
BEGIN;
SELECT id FROM lot_units
 WHERE lot_id = $1 AND status = 'available'
 ORDER BY id
 LIMIT 1
 FOR UPDATE SKIP LOCKED;
UPDATE lot_units
   SET status = 'reserved', reserved_by = $2,
       reserved_until = now() + interval '10 minutes'
 WHERE id = $3;
INSERT INTO outbox (...) VALUES (...);
COMMIT;
```

Обґрунтування за метриками:

- **Коректність:** взаємне виключення забезпечує менеджер блокувань
  PostgreSQL у межах ACID-транзакції; зовнішній координатор відсутній,
  тому розбіжність між блокуванням і даними неможлива.
- **Затримка:** транзакція не очікує на заблоковані рядки; час
  утримання блокування обмежено двома запитами за індексом
  `(lot_id, status)` та вставкою outbox-запису. Гіпотеза про
  відповідність p95 ≤ 250 мс підлягає перевірці стрес-тестом k6
  `spike-booking` у Розділі 3; у разі невідповідності рішення
  переглядається (див. «Перегляд рішення»).
- **Модель даних:** кожна одиниця має ідентифікатор, на який
  посилаються резерв, замовлення, QR-код і webhook до B2B-системи.
- **Інфраструктура:** нових компонентів не додається; Redis не бере
  участі в гарантії коректності.

## Consequences

**Позитивні:**

- Гарантія відсутності подвійного продажу перевіряється детермінованим
  стрес-тестом k6 (SRS-NFR-CONS-01).
- Резерв, оплата й outbox-подія фіксуються атомарно в одній транзакції.
- Відсутня потреба в fencing-токенах і моніторингу окремого
  сервісу блокувань.

**Негативні та ризики:**

- **Write amplification:** при імпорті лота створюється `quantity`
  рядків; для 10 000 лотів по 20 одиниць — 200 000 рядків, що
  потребує регулярного `VACUUM` і часткового індексу
  `WHERE status = 'available'`.
- **Відсутність справедливості (fairness):** `SKIP LOCKED` не гарантує
  порядку FIFO; користувач, запит якого надійшов першим, може не
  отримати одиницю. Для MVP ризик прийнято й зафіксовано в описі
  продукту.
- **Хибна відповідь «розпродано»:** `SKIP LOCKED` пропускає одиниці,
  заблоковані транзакціями, що згодом виконають ROLLBACK; запит може
  отримати 409 за наявності вільної одиниці. Клієнт повинен повторити
  запит один раз через 200 мс.
- **Тиск на пул з'єднань:** кожне резервування утримує з'єднання на
  час транзакції; при зростанні навантаження понад 300 RPS необхідно
  додати PgBouncer у режимі transaction pooling.
- **Прив'язка до СУБД:** рішення залежить від семантики блокувань
  PostgreSQL (аналог є в MySQL 8.0+, відсутній у більшості NoSQL);
  перехід на іншу СУБД потребує перегляду ADR.
- **Ускладнення CI/CD:** коректність перевіряється лише на реальній
  PostgreSQL, тому інтеграційні тести використовують Testcontainers,
  що додає близько 1–2 хв до конвеєра GitHub Actions і вимагає
  Docker-in-runner.
- **Масштабування СУБД:** горизонтальне масштабування запису
  (шардинг за `venue_id`) не розглядається; єдиний вузол PostgreSQL
  залишається точкою відмови, що компенсується RPO ≤ 24 год
  (SRS-NFR-REL-02).
- **FinOps:** додаткових витрат на керований Redis-кластер для блокувань
  немає; витрати на СУБД зростають через обсяг `lot_units` і
  WAL-трафік.

## Перегляд рішення

Рішення переглядається, якщо стрес-тест показує p95 > 250 мс при
200 VU або вимоги до справедливості черги стануть обов'язковими.
