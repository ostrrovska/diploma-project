## 1.2. Огляд сучасних підходів до вирішення задач дослідження

Предмет дослідження охоплює три класи інженерних задач: формування
ціни товару з обмеженим терміном придатності, контроль конкурентного
доступу до обмеженого інвентарю та доставку змін стану клієнтам у
реальному часі.

### 1.2.1. Підходи до ціноутворення товарів з обмеженим терміном придатності

1. **Статична уцінка (markdown pricing).** Знижку фіксовано заздалегідь
   (наприклад, −50% за дві години до закриття). Реалізація зводиться
   до правила в CRUD-системі; попит і залишок не враховуються.
2. **Покрокова (rule-based) уцінка.** Ціна знижується дискретними
   кроками за розкладом. Підхід поширений у ритейлі (електронні цінники),
   однак крок і частота підбираються емпірично.
3. **Безперервна функція спаду (Price Decay, аналог голландського
   аукціону).** Ціна є монотонно спадною функцією часу до закриття
   `P(t) = P_min + (P_0 − P_min) · (t_rem / T)^k`, де показник `k`
   задає форму кривої. Підхід створює стимул до раннього викупу й
   детермінований, що дозволяє перевіряти його модульними тестами.
4. **Прогнозна (ML-based) оптимізація ціни.** Модель прогнозу попиту
   (градієнтний бустинг, часові ряди) визначає ціну, що максимізує
   sell-through. Підхід потребує історичних даних і пакетного навчання,
   тому для MVP без історії продажів не застосовується.

У роботі обрано підхід 3 з можливістю калібрування параметра `k`
за накопиченими даними.

### 1.2.2. Підходи до контролю конкурентного доступу до інвентарю

| Підхід | Механізм | Обмеження |
|---|---|---|
| Песимістичне блокування СУБД | `SELECT … FOR UPDATE` | черга очікування на «гарячому» рядку |
| `FOR UPDATE SKIP LOCKED` | пропуск заблокованих рядків | вимагає моделювання лота як набору одиниць |
| Оптимістичне блокування | версія рядка, повтор при конфлікті | лавина повторів під піковим навантаженням |
| Розподілений лок (Redis `SET NX PX`) | зовнішній координатор | додатковий компонент, ризик розсинхронізації з СУБД |
| Серіалізація через чергу | один споживач на лот | додаткова затримка, складність повернення відповіді |

Для односерверної PostgreSQL-конфігурації `SELECT FOR UPDATE SKIP
LOCKED` забезпечує атомарне резервування одиниці лота без зовнішнього
координатора: конкурентні транзакції не очікують одна одну, а
отримують наступну вільну одиницю або порожній результат.

### 1.2.3. Підходи до доставки змін стану в реальному часі

- **Short polling** — клієнт опитує API з фіксованим інтервалом;
  навантаження зростає як `N_clients / interval`, затримка дорівнює
  половині інтервалу в середньому.
- **Server-Sent Events** — односпрямований потік поверх HTTP;
  обмежена підтримка в мобільних середовищах.
- **WebSocket (RFC 6455)** — двоспрямований канал із підпискою на
  кімнати (заклад, геокомірка); горизонтальне масштабування вузлів
  забезпечується через Redis pub/sub-адаптер.

Обрано WebSocket із Redis-адаптером як підхід із мінімальною
затримкою доставки та керованим навантаженням на API.

## 1.3. Аналіз та порівняння існуючих рішень на ринку

### 1.3.1. Технічний опис аналогів

#### Too Good To Go

Архітектурний патерн: мікросервісна архітектура на засадах
доменно-орієнтованого проєктування (DDD) із гексагональною
архітектурою (ports & adapters); Java 21 / Spring Boot; Kubernetes,
мультирегіональне розгортання на AWS.
Протоколи: REST (синхронно); AWS SQS, AWS SNS (асинхронно).
Стек даних: MySQL (транзакційна), ElasticSearch (пошук/гео), Redis
(кеш).
Обмеження: модель Surprise Bag без ідентифікації SKU; розділення
транзакційного й пошукового шарів створює ризик eventual
consistency; відсутнє геопросторове розширення рівня PostGIS.

#### Ticketmaster

Архітектурний патерн: шарована розподілена архітектура з
триступеневим захистом подвійного продажу (Redis NX-лок з TTL →
оптимістичне блокування СУБД → UNIQUE-constraint).
Протоколи: WebSocket/SSE; віртуальна черга на Redis (ZADD, FIFO,
JWT-токени допуску).
Стек даних: PostgreSQL + PgBouncer; Redis (300K+ reads/sec).
Обмеження: нелінійне зростання складності через три незалежні
механізми захисту; TTL-вікно звужує конкурентну пропускну
здатність; віртуальна черга додає затримку навіть за наявності
вільного інвентарю.

#### Karma

Архітектурний патерн: мікросервісна архітектура на керованому
Google Kubernetes Engine; поетапна міграція з bare-metal (Digital
Ocean) на GCP.
Протоколи: Google Cloud Pub/Sub (асинхронно); Cloud Functions,
Cloud Run (event-driven).
Стек даних: BigQuery (OLAP), BigQuery ML для прогнозування попиту.
Обмеження: аналітичний контур оптимізовано під пакетне
прогнозування, а не потоковий перерахунок ціни лота в реальному
часі; організаційний ризик compartmentalised domain knowledge.

### 1.3.2. Порівняльна інженерна матриця

| Критерій | Тема 1 | Too Good To Go | Ticketmaster | Karma |
|---|---|---|---|---|
| Тип архітектури | Сервісна: NestJS-сервіси (Core API, Trading, Worker, Realtime) у Docker | Мікросервісна (DDD, Kubernetes) | Шарована розподілена | Мікросервісна (GKE) |
| Протоколи обміну | REST + WebSocket + черга BullMQ | REST + SQS/SNS | WebSocket/SSE + Redis-черга | Pub/Sub, Cloud Functions |
| СУБД / сховище | PostgreSQL + PostGIS, Redis | MySQL + ElasticSearch | PostgreSQL + PgBouncer | BigQuery (OLAP) |
| Контроль конкурентного доступу | SELECT FOR UPDATE SKIP LOCKED | не розкрито | Redis-лок + optimistic lock + UNIQUE | не розкрито |
| Геопросторові можливості | PostGIS, GiST, ST_ClusterDBSCAN | ElasticSearch-індекс | не застосовується | не розкрито |
| Хмарна інфраструктура | Docker Compose + GitHub Actions | AWS, multi-region K8s | CDN, автомасштабування | GCP (GKE, Cloud Run) |

### 1.3.3. Аналітичний висновок

Порівняльний аналіз демонструє, що жоден із трьох проаналізованих
аналогів не поєднує в одній системі єдину СУБД для транзакційних і
геопросторових даних, детерміноване блокування конкурентного
доступу на рівні бази даних та потоковий перерахунок ціни лота в
реальному часі. Too Good To Go розділяє транзакційний і
пошуково-геопросторовий шари, що створює ризик часової
неузгодженості даних. Порівняння з Ticketmaster підтверджує
обґрунтованість обраного підходу до конкурентного бронювання:
триступеневий захист є надлишковою складністю для односерверного
MVP, тоді як SELECT FOR UPDATE SKIP LOCKED забезпечує еквівалентну
гарантію атомарності без розподіленого компонента. Приклад Karma
демонструє, що аналітичний контур індустрії орієнтовано на
пакетне прогнозування попиту, а не на потоковий Price Decay, що
підтверджує відсутність дублювання наявного галузевого рішення.

## 1.4. Аналіз предметної області (модель As-Is)

### 1.4.1. Загальна характеристика домену

Предметною областю є цифровий перерозподіл харчових продуктів з
обмеженим терміном придатності (surplus food redistribution) між
закладами харчування чи ритейлом та кінцевими споживачами. За
оцінкою UNEP Food Waste Index Report 2024, у 2022 році у світі
втрачено близько 1,05 млрд т харчових продуктів (19% доступних
споживачам), з них приблизно 28% — у секторі громадського
харчування. Переглянута Рамкова директива ЄС про відходи (2025)
встановлює цільове скорочення харчових відходів у роздрібній
торгівлі та споживанні на 30% на особу до 2030 року, що формує
регуляторний попит на програмні засоби перерозподілу.

Станом на 2026 рік у домені встановлено такі технологічні тренди:
перехід від статичних каталогів до подієво-орієнтованих систем
реального часу; використання геопросторових запитів як основного
способу навігації користувача; застосування ML-моделей прогнозу
попиту в аналітичному (пакетному) контурі; інтеграція B2B-систем
обліку залишків закладів із B2C-вітринами через API замість
ручного введення.

### 1.4.2. Ключові актори та сутності

**Актори:**

| Актор | Роль у системі |

### 1.4.3. Бізнес-процеси та вузькі місця (As-Is)

**Процес 1. Публікація та уцінка лота (статична модель).**
Заклад наприкінці дня вручну створює «пакунок» у веб-кабінеті
аналога з фіксованою ціною (зазвичай 1/3 від роздрібної). Ціна не
змінюється до моменту видачі. Дані про лот потрапляють у
транзакційну СУБД, а в пошуковий індекс — асинхронно.

- *B1.1:* ціна не залежить від залишку часу і попиту — у першій
  половині вікна продажу стимул до купівлі відсутній, у другій
  виникає пік запитів;
- *B1.2:* ручне введення лотів у кабінеті аналога дублює облік у
  касовій чи B2B-системі закладу (подвійне введення, розбіжність
  залишків);
- *B1.3:* затримка індексації (eventual consistency між MySQL та
  ElasticSearch) спричиняє показ лотів, які вже продано.

**Процес 2. Конкурентна купівля останніх одиниць лота.**
Клієнт отримує залишок із кешу або пошукового індексу, натискає
«Купити», API перевіряє залишок (`SELECT quantity`) і лише потім
зменшує його (`UPDATE`). Між перевіркою та оновленням відсутня
атомарність (check-then-act).

- *B2.1:* стан гонитви (race condition) під час одночасних запитів
  на один рядок призводить до подвійного продажу або до від'ємного
  залишку;
- *B2.2:* у разі захисту через `SELECT … FOR UPDATE` без
  `SKIP LOCKED` запити шикуються в чергу на «гарячому» рядку, p95
  затримка зростає лінійно з кількістю конкурентних запитів;
- *B2.3:* оплата виконується до фіксації резерву, тому конфлікт
  виявляється після списання коштів і потребує компенсаційного
  повернення (refund).

**Процес 3. Доставка актуальної ціни та залишку клієнтам.**
Мобільний клієнт аналогів оновлює список лотів через періодичне
опитування API (pull-to-refresh, short polling) або отримує
push-сповіщення без актуальної ціни.

- *B3.1:* затримка відображення змін дорівнює інтервалу опитування
  (15–60 с), що в умовах розпродажу є більшим за час вичерпання
  лота;
- *B3.2:* навантаження на API зростає пропорційно кількості
  активних клієнтів незалежно від факту зміни даних;
- *B3.3:* відсутній механізм відкладеної купівлі — користувач
  змушений вручну відстежувати ціну.

### 1.4.4. Регуляторні та індустріальні обмеження

- **Захист персональних даних:** GDPR (Regulation (EU) 2016/679) та
  Закон України «Про захист персональних даних» № 2297-VI;
  геолокація користувача є персональними даними — необхідні
  мінімізація, згода та право на видалення.
- **Платіжні дані:** PCI DSS v4.0 — номер картки не обробляється
  системою; оплата делегується сертифікованому провайдеру
  (tokenization / hosted checkout).
- **Безпека API:** OWASP API Security Top 10 (2023), OWASP ASVS 5.0
  (рівень L1–L2); автентифікація на JWT (RFC 7519).
- **Стандарти обміну даними:** OpenAPI 3.1 для REST-контракту з
  B2B-системою; RFC 6455 (WebSocket); RFC 3339 для міток часу;
  WGS 84 (EPSG:4326) для координат; ISO 4217 для валюти; RFC 9457
  (Problem Details) для формату помилок.
- **Харчова безпека:** продаж лота після `expires_at` заборонено —
  система зобов'язана автоматично знімати прострочені лоти з
  продажу.

### 1.4.5. Обґрунтування необхідності автоматизації

Виявлені вузькі місця B1.1–B3.3 мають спільну причину: відсутність
у наявних рішеннях атомарної моделі інвентарю та подієвого
контуру поширення змін ціни. Усунення B1.1 і B3.3 потребує
алгоритму безперервного ціноутворення та фонового матчингу
лімітних ордерів; B2.1–B2.3 — транзакційного механізму
резервування на рівні СУБД; B1.3 і B3.1–B3.2 — єдиного джерела
істини для транзакційних і геопросторових даних та push-доставки
змін через WebSocket.

## 1.5. Постановка задачі та формування вимог (модель To-Be)

### 1.5.1. Концептуальна модель To-Be

1. **Інтеграція фіду лотів.** B2B-система (Тема 2) передає лоти
   через REST-ендпоінт `POST /integration/v1/lots` з HMAC-підписом
   і ключем ідемпотентності; Core API виконує upsert у PostgreSQL
   і створює `N` записів `LotUnit`. Подвійне введення (B1.2)
   ліквідовано.
2. **Безперервне ціноутворення.** Pricing Worker кожні 60 с
   отримує задачу з черги BullMQ, перераховує ціну активних лотів
   за функцією Price Decay пакетним `UPDATE` і публікує подію
   `price.updated` у Redis pub/sub. Ціна стає функцією часу (B1.1).
3. **Доставка змін.** Realtime Gateway отримує подію і транслює її
   клієнтам, підписаним на кімнату закладу або геокомірки, через
   WebSocket. Опитування API замінено push-моделлю (B3.1, B3.2).
4. **Лімітні ордери.** Після кожного перерахунку Worker вибирає
   ордери з `threshold ≥ current_price` та ініціює для них
   автоматичне резервування (B3.3).
5. **Атомарне резервування.** Trading Service у межах однієї
   транзакції виконує `SELECT id FROM lot_units WHERE lot_id = $1
   AND status = 'available' LIMIT 1 FOR UPDATE SKIP LOCKED`, змінює
   статус на `reserved` з TTL 10 хв і лише після цього ініціює
   оплату. Подвійний продаж (B2.1) і черга на «гарячому» рядку
   (B2.2) виключені; оплата не починається без резерву (B2.3).
6. **Єдине джерело істини.** Пошук лотів за радіусом виконується
   запитом PostGIS (`ST_DWithin` з GiST-індексом) до тієї самої
   СУБД, що й транзакції; розбіжність індексу (B1.3) виключено.

### 1.5.2. Функціональні вимоги (Core Features)

**Модуль Integration (Core API)**
- **CF-1.** Приймати фід лотів від B2B-системи через REST з перевіркою
  HMAC-SHA256 підпису та ідемпотентним upsert.

**Модуль Auth (Core API)**
- **CF-2.** Реєструвати та автентифікувати користувача з видачею
  access JWT (RS256, 15 хв) і ротацією refresh-токена.

**Модуль Geo (Core API)**
- **CF-3.** Шукати заклади з активними лотами в заданому радіусі та
  кластеризувати їх для мапи (`ST_ClusterDBSCAN`).

**Модуль Pricing (Pricing Worker)**
- **CF-4.** Перераховувати ціну кожного активного лота за функцією
  Price Decay за розкладом (інтервал 60 с) та знімати з продажу лоти
  з вичерпаним `expires_at`.

**Модуль Booking (Trading Service)**
- **CF-5.** Резервувати одиницю лота атомарно через `SELECT FOR UPDATE
  SKIP LOCKED` з TTL резерву та автоматичним звільненням після його
  спливу.
- **CF-6.** Підтверджувати замовлення після callback платіжного
  провайдера (sandbox) з перевіркою підпису та передавати
  підтвердження продажу B2B-системі.

**Модуль Limit Orders (Trading Service + Pricing Worker)**
- **CF-7.** Створювати та скасовувати лімітний ордер з пороговою ціною
  і автоматично виконувати резервування при досягненні порога.

**Модуль Realtime (Realtime Gateway)**
- **CF-8.** Транслювати оновлення ціни та залишку лота підписаним
  клієнтам через WebSocket-кімнати.

**Допоміжні функції (поза алгоритмічним ядром):** нарахування балів
впливу, титули та щоденний decay балів (модуль Gamification).

### 1.5.4. Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та
розробка B2C-підсистеми маркетплейсу сервісної архітектури
(NestJS-сервіси, PostgreSQL/PostGIS, Redis, BullMQ, WebSocket) для
вирішення задачі динамічного ціноутворення та гарантовано
коректного конкурентного бронювання лотів з обмеженим терміном
придатності. Система має забезпечити перерахунок ціни за функцією
Price Decay з інтервалом 60 с, атомарне резервування одиниці лота
без подвійного продажу при 200 одночасних запитах (p95 ≤ 250 мс),
автоматичне виконання лімітних ордерів, геопросторовий пошук
(p95 ≤ 150 мс при 300 RPS) і доставку змін ціни клієнтам через
WebSocket із затримкою p95 ≤ 2 с, а також інтеграцію з незалежною
B2B-системою через REST API-контракт.

## Висновки до розділу 1

Аналіз ринку та сучасних підходів встановив, що наявні рішення
перерозподілу харчових продуктів реалізують статичну модель
уцінки й синхронну обробку замовлень із розділенням
транзакційного і пошукового сховищ. Така архітектура не створює
цінового стимулу до раннього викупу, допускає показ неактуального
інвентарю через eventual consistency та не гарантує атомарності
резервування під час пікового конкурентного доступу. Рішення з
галузі квиткових систем (Ticketmaster) усувають подвійний продаж
ціною трьох незалежних механізмів блокування, що є надлишковим
для системи з одним вузлом СУБД.

Обґрунтовано, що виявлені вузькі місця усуваються поєднанням
трьох механізмів: безперервної функції Price Decay з фоновим
перерахунком через чергу BullMQ, транзакційного резервування
`SELECT FOR UPDATE SKIP LOCKED` у PostgreSQL та push-доставки змін
через WebSocket із Redis pub/sub. Використання PostgreSQL з
розширенням PostGIS як єдиного джерела істини для транзакційних і
геопросторових даних виключає розбіжність індексів, а розподіл
логіки між Core API, Trading Service, Pricing Worker і Realtime
Gateway дозволяє масштабувати навантажені компоненти незалежно.

Сформовано вісім функціональних вимог (Core Features) за сімома модулями та 18
нефункціональних вимог із числовими межами (p95 Latency, RPS,
RPO/RTO, стандарти безпеки). Аналітичне обґрунтування архітектури,
специфікація вимог за ISO/IEC/IEEE 29148, моделювання системи за
C4 Model та фіксація архітектурних рішень стануть предметом
Розділу 2 (Проєктування), а безпосередня технічна реалізація
вимог і їх інструментальна верифікація — предметом Розділу 3
(Реалізація).
