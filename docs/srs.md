# Специфікація вимог до програмного забезпечення (SRS)

Документ сформовано за структурою ISO/IEC/IEEE 29148:2018.
Версія 1.0 від 18.10.2026, статус: Baseline.
Джерело вимог: [1_analysis.md, підрозділ 1.5](./1_analysis.md#15-постановка-задачі-та-формування-вимог-модель-to-be).
Архітектурне трасування: [2_design.md](./2_design.md).

## 1. Призначення та межі

**Призначення.** Документ фіксує контракт вимог до B2C-підсистеми
маркетплейсу перерозподілу товарів з обмеженим терміном
придатності: динамічне ціноутворення, лімітні ордери, конкурентне
бронювання лотів, геопросторовий пошук і доставка змін у реальному
часі.

**Межі (Scope).** До системи входять: мобільний клієнт, API Gateway,
сервіси Core API, Trading Service, Pricing Worker, Realtime Gateway,
сховища PostgreSQL/PostGIS і Redis, контур спостережуваності. Поза
межами системи: B2B-система закладів (Тема 2), платіжний провайдер,
сервіс push-сповіщень, постачальник картографічних тайлів.

**Конвенції.** «Повинна» — обов'язкова вимога. Пріоритет за MoSCoW:
M (Must), S (Should), C (Could).

## 2. Контекст системи (System Context)

| Зовнішня сутність | Тип | Взаємодія з системою | Протокол |
|---|---|---|---|
| Покупець | Person | пошук, купівля, лімітні ордери, отримання змін ціни | HTTPS (REST), WSS |
| Адміністратор платформи | Person | модерація закладів, параметри Price Decay, моніторинг | HTTPS (REST), Grafana UI |
| B2B-система (Тема 2) | External System | надсилає фід лотів; отримує підтвердження продажу | REST / HTTPS, HMAC-SHA256 |
| Платіжний провайдер (LiqPay, sandbox) | External System | hosted checkout; callback про статус оплати | HTTPS, підпис callback |
| Expo Push Service / FCM | External System | доставка push-сповіщень про виконання ордера | HTTPS |
| OpenStreetMap tiles | External System | картографічна підкладка в мобільному клієнті | HTTPS |

Система не зберігає номери платіжних карток і не виконує функцій
облікової системи закладу.

## 3. Функціональні вимоги

### SRS-FUN-01

**Integration, M.** Система повинна приймати фід лотів від B2B-системи
через `POST /integration/v1/lots` і відхиляти запит з кодом 401, якщо
HMAC-SHA256 підпис у заголовку `X-Signature` не збігається.

### SRS-FUN-02

**Integration, M.** Система повинна виконувати ідемпотентний upsert лота
за ключем `(merchant_id, external_lot_id)` і створювати `quantity`
записів `LotUnit` у статусі `available` в одній транзакції.

### SRS-FUN-03

**Auth, M.** Система повинна реєструвати користувача за email і паролем,
зберігаючи пароль лише як хеш Argon2id.

### SRS-FUN-04

**Auth, M.** Система повинна видавати access JWT (RS256, строк дії 15 хв)
і refresh-токен (30 діб) та анулювати попередній refresh-токен під час
кожного оновлення (rotation).

### SRS-FUN-05

**Geo, M.** Система повинна повертати заклади з активними лотами в
радіусі від 0,5 до 10 км від заданої точки WGS 84, відсортовані за
відстанню.

### SRS-FUN-06

**Geo, S.** Система повинна повертати кластери закладів для
прямокутника мапи (bbox), обчислені `ST_ClusterDBSCAN` з параметром
`eps`, залежним від масштабу.

### SRS-FUN-07

**Pricing, M.** Система повинна перераховувати ціну кожного активного
лота з інтервалом 60 с за функцією
`P(t) = P_min + (P_0 − P_min) · (t_rem / T)^k` з округленням до 0,01
грн.

### SRS-FUN-08

**Pricing, M.** Система повинна переводити лот у статус `expired`, коли
поточний час досягає `expires_at`, і відхиляти резервування такого
лота.

### SRS-FUN-09

**Booking, M.** Система повинна резервувати рівно одну одиницю лота в
межах однієї транзакції через `SELECT … FOR UPDATE SKIP LOCKED`,
фіксуючи ціну на момент резервування, і повертати код 409, якщо
вільних одиниць немає.

### SRS-FUN-10

**Booking, M.** Система повинна звільняти резерв і повертати одиницю в
статус `available`, якщо оплату не підтверджено протягом 10 хв.

### SRS-FUN-11

**Booking, M.** Система повинна переводити замовлення в статус `paid`
лише після callback платіжного провайдера з валідним підписом;
повторний callback для того самого замовлення не повинен змінювати
стан (ідемпотентність).

### SRS-FUN-12

**Integration, M.** Система повинна надсилати B2B-системі webhook
підтвердження продажу через transactional outbox з не менш ніж
трьома повторами за exponential backoff.

### SRS-FUN-13

**Limit Orders, M.** Система повинна створювати лімітний ордер із
пороговою ціною для конкретного лота та дозволяти його скасування до
моменту виконання.

### SRS-FUN-14

**Limit Orders, M.** Система повинна ініціювати резервування за
лімітним ордером не пізніше ніж через 5 с після того, як ціна лота
стала меншою або рівною пороговій.

### SRS-FUN-15

**Realtime, M.** Система повинна надсилати подію `lot.price_updated`
або `lot.stock_updated` усім WebSocket-клієнтам, підписаним на кімнату
відповідного закладу.

### SRS-FUN-16

**Rate Limiting, M.** Система повинна відхиляти запити з кодом 429 при
перевищенні 100 запитів/хв на користувача або 10 спроб резервування/хв.

### SRS-FUN-17

**Privacy, M.** Система повинна видаляти або анонімізувати персональні
дані користувача протягом 30 діб після запиту на видалення акаунта.

### SRS-FUN-18

**Gamification, C.** Система повинна нараховувати бали впливу за кожне
замовлення в статусі `paid` та зменшувати баланс на 2% щоденно.

### SRS-FUN-19

**Administration, S.** Система повинна дозволяти адміністратору змінювати
параметри Price Decay (`k`, відношення `P_min / P_0`) для закладу;
нові параметри повинні застосовуватися з наступного циклу перерахунку.

### SRS-FUN-20

**Realtime, M.** Система повинна відхиляти WebSocket-з'єднання без
валідного access JWT під час handshake.

## 6. Глосарій

| Термін | Визначення |
|---|---|
| Лот (Lot) | партія однорідного товару закладу з початковою і мінімальною ціною та строком `expires_at` |
| Price Decay | монотонно спадна функція ціни лота від часу, що залишився до закриття |
| Лімітний ордер (Limit Order) | доручення користувача автоматично зарезервувати лот, коли ціна досягне порога |
| SKIP LOCKED | модифікатор `SELECT … FOR UPDATE` у PostgreSQL, який пропускає рядки, заблоковані іншими транзакціями |
| Latency p95 | значення часу відгуку, яке не перевищують 95% запитів у вибірці |
| JWT | JSON Web Token (RFC 7519): підписаний токен із claims користувача |
| Transactional Outbox | патерн запису вихідної події в ту саму транзакцію, що й зміну стану, з подальшою асинхронною доставкою |
| Eventual Consistency | модель узгодженості, за якої репліки сходяться до однакового стану через деякий час |
